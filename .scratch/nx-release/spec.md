# 为 REZoningAI 建立 Nx Release 流程

Status: resolved

## 问题陈述

REZoningAI 的 Web、API 和共享聊天包由 Nx 和 pnpm 管理，开发者已经通过 Husky 和 Commitlint 使用 Conventional Commits。三个包一起构建和运行，但目前只有根清单声明 `0.1.0`，仓库还没有发布 tag、变更日志或统一发布入口。维护者缺少一条可重复执行的流程来判断下一版本、验证待发布提交，并用 Git tag 标记可检出的应用版本。

## 解决方案

将 Web、API 和共享聊天包作为一个 Agent 应用，通过 `pnpm release` 发布。维护者先用 `--dry-run` 审阅版本、根变更日志和目标 tag，再从干净的 `main` 正式执行。格式、Lint、测试和构建全部通过后，Nx 生成一个版本提交和一个指向该提交的附注 tag，使用者可以按 tag 获取源码并沿用现有方式构建和运行。

| 场景 | 预演 | 正式发布 |
| --- | --- | --- |
| 首次发布 | `pnpm release 0.1.0 --first-release --dry-run` | `pnpm release 0.1.0 --first-release` |
| 后续发布 | `pnpm release --dry-run` | `pnpm release` |

## 用户故事

1. 作为发布维护者，我希望从仓库根目录调用统一的发布命令，以便按同一流程预演和正式发布。
2. 作为发布维护者，我希望 Web、API 和共享聊天包共用一个版本，以便每个发布版本对应一套完整的 Agent 应用。
3. 作为开发者，我希望根清单和三个包显示同一个版本，以便从任一清单识别所属的应用版本。
4. 作为首次发布的维护者，我希望沿用 `0.1.0` 并创建 `v0.1.0`，以便确定后续升版和变更日志的起点。
5. 作为发布维护者，我希望 Nx 根据上一个发布 tag 之后的 Conventional Commits 推导版本，以便复用团队现有的提交约定。
6. 作为维护 `0.x` 的开发者，我希望功能和修复升补丁，破坏性变更升次版本，以便按约定维护早期版本。
7. 作为发布维护者，我希望可以显式指定版本，以便在合适时发布 `1.0.0`。
8. 作为项目文档或独立原型的维护者，我希望只有文档或 Python 原型改动时自动发布不产生新版本，以便 Agent 按自身的变更发布。
9. 作为发布维护者，我希望预演能显示目标版本、日志和 tag，以便检查条目、版本幅度和 tag 是否可用。
10. 作为开发者，我希望在开发分支也能预演，以便在合入前审阅发布结果。
11. 作为发布维护者，我希望预演跳过全量质量检查，并且不写入版本文件或 Git 状态，以便快速反复审阅。
12. 作为发布维护者，我希望只有干净的 `main` 能正式发布，以便版本指向已提交的主分支代码。
13. 作为发布维护者，我希望暂存、未暂存或未跟踪的改动都能阻止正式发布，以便发布提交只包含此次发布生成的文件。
14. 作为发布维护者，我希望正式发布自动运行现有的格式、Lint、测试和构建检查，以便在写入发布结果前发现失败。
15. 作为贡献者，我希望自动生成的版本提交通过现有的提交消息校验，以便继续用同一套提交规范审查历史。
16. 作为应用使用者，我希望能通过一个附注 tag 找到对应的发布提交，以便检出源码并复现该版本。
17. 作为变更日志读者，我希望在仓库根目录看到版本日期、变更条目、提交引用和作者名，以便查阅发布内容及其出处。
18. 作为维护者，我希望日志使用 Nx 原生分类和发布区间，以便沿用工具的生成规则。发布区间内符合分类规则的独立原型提交也可以出现在日志中。
19. 作为发布维护者，我希望用本地 Git 生成发布交付物，以便在没有远端、注册表或平台账户的环境中操作。
20. 作为应用开发者，我希望升版后仍能按锁文件安装，并通过 `workspace:*` 解析共享聊天包，以便使用现有开发和构建入口。
21. 作为首次操作发布的维护者，我希望 README 说明如何核对预演结果、执行发布和处理提交或 tag 创建失败，以便判断故障后从哪里继续。

## 实施决策

- 沿用 Nx 24.0.6 和现有 pnpm 工作区。显式选定 `web`、`api` 和 `chat` 组成一个固定发布组。三个包在接入时补齐 `0.1.0`，根清单的版本通过 API 项目的 Nx 多清单更新配置同步。四份清单保留私有属性，内部依赖保留 `workspace:*`。
- 用 `v{version}` 标记发布提交。首次通过 `--first-release` 显式发布 `0.1.0`，之后由 Nx 使用匹配的历史 tag 和 Conventional Commits 推导下一版本。显式版本可覆盖推导结果。沿用 Nx 的零主版本调整和默认提交类型规则。
- 生成根 `CHANGELOG.md`，使用 Nx 默认渲染器和工作区日志范围。版本条目保留日期、提交引用及 Git 作者名，关闭在线用户名查询。应用升版按发布项目判定，根日志按整个 Git 区间生成。
- 发布入口调用 `nx release --skip-publish`，由 Nx 统一生成清单更新、根日志、符合 Commitlint 的版本提交和附注 tag。交付物保存在本地 Git，远端发布功能保持关闭。
- 用 Nx `preVersionCommand` 接入检查。预演跳过正式发布检查。正式执行时，先确认当前分支为 `main`，且工作区、暂存区均干净并且没有未跟踪文件，再依次执行 `pnpm format:check`、`pnpm lint`、`pnpm test`、`pnpm build`。任一步失败即在写入版本、日志或 tag 前退出。
- README 记录首次发布、自动升版和显式指定版本的用法，说明如何在预演后核对目标 tag、在正式执行后核对发布提交与 tag 的对应关系，以及如何根据 Git 状态处理版本提交或 tag 创建失败。新增 ADR 记录统一发布的边界和理由，实施工单记录验收结果。

## 测试决策

- 以维护者实际使用的 `pnpm release` 为主要验收入口。用退出状态、预演输出、文件内容、Git 索引、提交和 tag 验证外部行为。参考 Nx/pnpm 迁移、Commitlint 和格式化接入的先例，在干净的临时克隆中执行真实命令。
- 在 `main` 及另一分支预演，比较运行前后的清单、日志、暂存区、`HEAD` 和 tag，验证 Git 状态和文件内容保持一致，并确认未执行正式发布检查。
- 在临时克隆实际执行 `v0.1.0` 首发。验证根日志随唯一的版本提交写入，提交通过现有 Commitlint，附注 tag 指向该提交。随后真实执行一次后续发布，确认四份清单同步更新，日志新增版本条目，内部依赖仍为 `workspace:*`，并通过 `pnpm install --frozen-lockfile` 验证锁文件兼容性。
- 从 `v0.1.0` 分别构造 Agent 的 `fix`、`feat` 和破坏性提交，预演应分别得出 `0.1.1`、`0.1.1` 和 `0.2.0`。验证显式指定 `1.0.0` 可覆盖结果。分别验证只有文档提交和只有独立 Python 原型提交时，自动发布不产生版本提交或 tag。另在含 Agent 和原型变更的区间核对日志范围。
- 分别用非 `main` 分支、已暂存改动、未暂存改动、未跟踪文件和失败的质量检查触发正式发布。检查退出结果，并核对版本文件、日志、`HEAD`、tag 和原有工作区改动。

## 范围之外

- npm 或镜像注册表发布、构建产物分发、GitHub Release、自动推送和 CI/CD 工作流。
- 独立 Python 原型升版、历史提交改写、自定义变更日志渲染器或提交分类。
- 修改选址业务、聊天协议、API、数据结构或现有质量检查规则。
- 在实际仓库创建首个正式版本提交或 tag。

## 补充说明

维护者在流程合入后，从干净的 `main` 创建正式 `v0.1.0`。验收期间的版本提交和 tag 留在临时克隆。
