# 为 REZoningAI 接入 Nx 代码格式化

Status: resolved

## 问题陈述

REZoningAI 已用 Nx 和 pnpm 管理 Web、API 和共享聊天包，Husky 在提交时执行 ESLint 和 Commitlint。仓库目前缺少统一的格式化规则、修复命令和提交前格式检查。贡献者修改源码、测试或工具配置时，需要自行保持风格一致，审查时也容易混入与功能无关的格式差异。

## 解决方案

使用 Nx 原生支持的 Prettier，以根工作区配置统一代码和工具配置的格式。接入时一次性格式化存量文件，让首次全量检查通过。开发者在根目录运行 `pnpm format:write` 可修复格式，运行 `pnpm format:check` 可查看需要修复的文件。Husky 在每次提交前复用同一个只读检查入口。

## 用户故事

1. 作为贡献者，我希望安装工作区依赖后就能运行格式化，以便每个人使用锁定的工具版本。
2. 作为贡献者，我希望用一条命令格式化整个 Agent 工作区，以便一次修复所有受管文件。
3. 作为贡献者，我希望用一条只读命令查看格式问题，以便在修改文件前确认影响范围。
4. 作为 Web 开发者，我希望 TypeScript、React、HTML 和 CSS 都参与格式化，以便前端项目采用一致风格。
5. 作为 API 开发者，我希望源码和测试都参与格式化，以便测试改动也遵循同一套规则。
6. 作为共享聊天包维护者，我希望共享包使用相同的根配置，以便跨项目修改时获得一致的格式。
7. 作为工作区维护者，我希望根目录和各项目的工具配置都参与格式化，以便依赖清单、Nx 配置和工具脚本采用一致风格。
8. 作为使用 Nx 生成器的开发者，我希望生成文件时使用同一套格式规则，以便后续全量检查能使用相同的基线。
9. 作为贡献者，我希望 JavaScript 和 TypeScript 使用单引号并按 100 列宽度换行，以便保持常见表达式的可读性。
10. 作为独立原型维护者，我希望财务和工程概算原型连同 JSON 样例都留在格式化范围外，以便独立维护各自的文件。
11. 作为文档维护者，我希望 Markdown 和本地工单保留现有排版，以便文档修订由作者决定。
12. 作为工作区维护者，我希望生成产物、覆盖率报告、缓存和锁文件被排除，以便格式化只产生可审查的手写文件差异。
13. 作为首次使用该功能的贡献者，我希望干净安装后全量检查即可通过，以便后续诊断可以直接用于排查当前改动。
14. 作为提交者，我希望每次提交前都执行格式检查，即使本次只暂存了文档，以便及时发现完整工作区里的格式问题。
15. 作为提交者，我希望格式失败时看到文件路径并且提交被阻止，以便修复后重试。
16. 作为提交者，我希望钩子保留工作区和暂存区的内容，以便自己决定修复哪些文件及提交哪些改动。
17. 作为维护者，我希望通过格式检查后仍依次执行现有的 ESLint 和提交消息校验，以便每项检查继续履行原有职责。
18. 作为新贡献者，我希望 README 说明命令、覆盖范围和提交前行为，以便自行复现和处理诊断。
19. 作为仓库维护者，我希望在独立 worktree 中审查已经验收的待提交改动，以便决定何时集成。

## 实施决策

- 沿用 ADR 0007 的 Nx 与 pnpm 工作区。以当前 `main` 的 `557b307` 为基线，在独立 worktree 的 `codex/formatting` 分支实施，交付已验收的未提交改动。
- 一并更新根工作区开发依赖和 pnpm 锁文件。Prettier 采用 Nx 24.0.6 生成器选用的版本范围 `~3.6.2`。使用 Nx 可发现的根 Prettier 配置，显式设置 `singleQuote` 为 `true`、`printWidth` 为 `100`，其余使用 Prettier 默认值。
- 公开入口为运行全量写入的 `pnpm format:write` 和运行全量检查的 `pnpm format:check`。两者分别调用 Nx 内置的 `nx format:write --all` 和 `nx format:check --all`，共用根配置和忽略规则。
- 格式化 Web、API、共享聊天包的源码、测试、前端静态文件，以及项目内和根目录的工具配置。根 Prettier 忽略规则排除 Markdown、本地规格和工单、财务与工程概算原型、pnpm 锁文件、构建产物、覆盖率报告和 Nx 缓存。Nx 的 Prettier 扫描也读取根 Git 忽略规则，将本地环境文件、数据和依赖目录排除在外。
- 配置完成后运行一次全量写入，建立存量基线。审查格式差异，确保此次格式化保留应用行为和数据含义。
- Husky 的提交前钩子先执行全量格式检查，通过后执行 `pnpm lint`。检查读取磁盘上的完整工作区，未暂存的格式问题也会阻断提交。钩子只检查和报告，修复与暂存由提交者执行。提交消息继续由现有 Commitlint 钩子校验。
- README 记录公开命令、覆盖范围和提交前行为。实施工单记录实际验收结果。

## 测试决策

- 从贡献者实际调用的根命令和真实 Git 提交验收，以诊断路径、退出状态、文件内容、暂存区内容和是否创建提交作为证据。沿用 Nx 与 pnpm 迁移、ESLint 接入及 Commitlint 接入的临时仓库验收方式。
- 在干净副本执行 `pnpm install --frozen-lockfile`，确认 `pnpm format:check` 首次通过。连续运行全量写入并比较文件内容，确认基线的格式化结果可重复。
- 在临时副本为三个项目的源码或测试、前端静态文件及根工具配置制造可解析的格式偏差。确认检查返回失败并列出对应路径，且不改写文件。运行写入命令后再次检查，确认恢复通过。
- 在同一副本为 Markdown、本地工单、独立 Python 原型的 JSON 样例、锁文件和生成文件准备有格式偏差的样例。确认检查跳过这些文件，并在执行全量写入前后逐字节比对。
- 在临时 Git 仓库验证钩子。暂存一项无关改动，留下未暂存的格式问题，确认提交失败、`HEAD` 未移动、工作区文件和暂存区内容均保持一致。修复格式后，分别用格式合规的 ESLint 违规和不合规的提交消息验证两个现有钩子的拒绝行为，再以合规内容和消息验证提交成功。
- 执行 `pnpm lint`、`pnpm test` 和 `pnpm build`，验证现有代码检查、测试和构建通过。

## 范围之外

- Markdown 排版、独立 Python 原型及其样例的格式化。
- 新增 CI 或远程合并门禁、编辑器配置、暂存区专用格式检查和提交时自动修复。
- 修改 ESLint 或 Commitlint 规则，调整选址业务、聊天协议、API 或数据库结构。
