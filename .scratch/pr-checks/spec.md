# 为 REZoningAI 增加 PR 检查 CI

Status: accepted
Labels: ready-for-agent

## 问题陈述

维护者在本地可以检查 Agent 的格式、ESLint、测试和构建，但 GitHub 上的 PR 缺少自动验证合入结果的检查。本地结果无法说明待合入的改动是否能与最新的 `main` 一起通过检查。维护者需要在 PR 中看到统一的检查结果，并在检查失败或基线过期时阻止合并。

启用必需检查后，发布版本提交也要经过 PR。维护者仍需从干净的本地 `main` 生成版本提交和附注 tag，并确保该 tag 对应的原始提交进入远端 `main`。

## 解决方案

用 GitHub Actions 为所有指向 `main` 的 PR 运行 `Agent checks`。这个检查复用 Agent 的四项本地验证命令。将它设为 `main` 的必需状态检查，并要求 PR 与最新的 `main` 同步。发布时继续由 Nx Release 生成版本提交和附注 tag，先通过发布 PR 合入版本提交，再推送 tag。

## 用户故事

1. 作为 PR 作者，我希望打开指向 `main` 的 PR 后自动运行 Agent 检查，以便在提交审阅后看到待合入代码的验证结果。
2. 作为 PR 作者，我希望更新 PR 分支后重新运行检查，以便确认修复和后续提交已经过验证。
3. 作为 PR 作者，我希望重新打开 PR 或把目标分支改为 `main` 时运行检查，以便继续使用同一套合并条件。
4. 作为文档贡献者，我希望纯文档 PR 也产生同名检查结果，以便满足 `main` 的合并门禁。
5. 作为 Agent 开发者，我希望 CI 使用仓库声明的 pnpm 版本和冻结的锁文件，以便在干净环境中复现依赖安装。
6. 作为 Agent 开发者，我希望 CI 执行现有格式检查，以便发现本地提交前未处理的格式问题。
7. 作为 Agent 开发者，我希望 CI 执行现有 ESLint 检查，以便发现 Web、API 和共享聊天包中的规则错误。
8. 作为 Agent 开发者，我希望 CI 运行现有 API 测试，以便验证聊天链路和恢复行为，并且无需配置真实模型凭据。
9. 作为 Agent 开发者，我希望 CI 执行生产构建，以便发现 Web、API 和共享聊天包组合后的构建问题。
10. 作为 PR 作者，我希望从 Actions 日志看到安装或检查失败的具体步骤，以便定位问题并重新提交修复。
11. 作为 PR 审阅者，我希望在 PR 中看到固定名称的必需状态检查，以便判断待合入代码是否已通过验证。
12. 作为仓库维护者，我希望检查失败或尚未得出成功结果时无法合并，以便 `main` 只接收经过验证的改动。
13. 作为仓库维护者，我希望 PR 在 `main` 前进后同步基线并接受验证，以便检查包含最新的已合入变更。
14. 作为仓库管理员，我希望自己也受同一门禁约束，以便发布和日常变更遵循同一套检查。
15. 作为仓库维护者，我希望先审阅并合并启用工作流的 PR，再启用分支规则，以便可以先确认 GitHub 已收到成功结果。
16. 作为发布维护者，我希望继续使用本地 Nx Release 生成版本提交、变更日志和附注 tag，以便延续 Agent 的统一发布流程。
17. 作为发布维护者，我希望发布 PR 以合并提交方式合入原始版本提交，以便本地生成的附注 tag 仍指向 `main` 历史中的同一个提交。
18. 作为发布维护者，我希望在确认版本提交已进入远端 `main` 后才推送 tag，以便使用者按 tag 检出的版本已通过合并门禁。
19. 作为发布维护者，我希望在发布期间基线前进时能从最新的 `main` 重新生成发布结果，以便版本提交和 tag 包含最新基线。

## 实施决策

- 工作流以目标分支为 `main` 的 `pull_request` 事件触发，覆盖创建、更新、重开和改投 `main` 的情况。检查 GitHub 生成的待合入结果。所有符合条件的 PR 运行同一个名为 `Agent checks` 的检查，无路径过滤。
- 使用 GitHub 托管的 Linux runner、Node.js 24，以及根包清单声明的 pnpm 版本。以只读仓库权限检出代码，执行 `pnpm install --frozen-lockfile`，随后依次执行 `pnpm format:check`、`pnpm lint`、`pnpm test` 和 `pnpm build`。安装或任一步骤失败时，检查失败。API 测试使用现有模拟模型接口和临时 SQLite。
- Commitlint 继续由本地 Git 钩子执行，工程概算和财务 Python 原型沿用各自的本地验证命令。PR 工作流使用 Agent 的现有检查入口和规则。
- 在独立分支提交工作流与 README 改动，保留原有工作区修改。先创建实施 PR 并确认 `Agent checks` 成功，由仓库维护者审阅和合并。合并后将 GitHub Actions 报告的 `Agent checks` 设为 `main` 的必需状态检查，要求分支与最新的 `main` 同步。这条规则适用于管理员且没有绕过条目。保留其他现有分支规则。
- README 记录 PR 检查及发布步骤。正式发布仍在干净且同步的本地 `main` 运行 `pnpm release`。生成版本提交和附注 tag 后，将版本提交推到发布分支并通过 PR 合入。发布 PR 使用 GitHub 的合并提交方式，确认原始版本提交已进入远端 `main` 后，再单独推送指向它的附注 tag。若待合入期间 `main` 前进，从最新的干净 `main` 重新生成版本提交和仍未推送的 tag，并用新的发布提交更新 PR。

## 测试决策

- 以 GitHub PR 的检查结果和 `main` 的生效规则为主要验收入口。以现有根目录命令为本地入口，参考现有 Nx Release 正式发布前的四项检查。验证可观察结果，包括步骤退出状态、Actions 日志、PR 检查状态和 Git 提交关系。
- 在实施分支验证工作流语法、冻结锁文件安装及四项现有检查。用临时检出的格式错误验证格式检查返回非零退出状态，故障样例留在临时检出中。
- 在实施 PR 中确认 `Agent checks` 由面向 `main` 的 PR 事件触发，并通过格式、ESLint、API 测试和构建。核对工作流没有以文件路径跳过纯文档改动。仓库维护者合并后，确认 `main` 的生效规则指定同名检查和 GitHub Actions 来源、要求最新基线，且没有绕过条目。
- 按 README 核对发布顺序和提交关系。发布 PR 合入后，附注 tag 指向的原始版本提交应是远端 `main` 的祖先。可在临时 Git 检出中验证提交关系，正式版本和 tag 由维护者按发布计划创建。

## 范围之外

- 在 GitHub Actions 中运行工程概算和财务测试，或检查 PR 标题与提交消息。
- 为 `main` 推送单独运行 CI，自动升版、推送 tag、部署或创建 GitHub Release。
- 修改 Agent、聊天协议、选址业务、Python 原型或现有质量检查规则。
- 执行仓库的正式版本发布。

## 补充说明

规划阶段的本地基线已通过格式、ESLint 和构建。API 测试需要在回环地址启动模拟服务，本地沙箱拒绝监听 `127.0.0.1`，以实施 PR 的线上结果验收。
