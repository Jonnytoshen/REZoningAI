# Agent 基础版的 Nx 和 pnpm 迁移

Status: ready-for-agent

## 问题陈述

Agent 基础版的 Web 和 API 虽然有各自的源码目录，仍共用一份 npm 依赖清单、一组根脚本和跨目录相对导入。开发者只能通过手写脚本编排构建和启动，难以从依赖声明看出每个应用所需的包，也无法用统一的项目图判断修改共享聊天代码会影响哪些构建和测试。

## 解决方案

用 pnpm 工作区管理 Web、API 和共享聊天模块的依赖，用 Nx 管理项目图、任务顺序和本地缓存。开发者继续从仓库根目录安装依赖、启动服务、构建和测试。开发和测试直接使用共享模块源码，生产构建生成 JavaScript，运行时仍由 Nest 在同一个本机端口提供 Web 页面和 API。

## 用户故事

1. 作为首次接手仓库的开发者，我希望从 README 知道需要的 Node.js 和 pnpm 版本，以便使用与团队一致的工具链。
2. 作为开发者，我希望从根目录按锁文件安装全部 TypeScript 项目的依赖，以便在干净环境中复现构建。
3. 作为 Web 开发者，我希望 Web 包声明它直接使用的依赖，以便判断前端变更涉及哪些依赖。
4. 作为 API 开发者，我希望 API 包声明它直接使用的依赖，以便单独维护后端工具和运行时依赖。
5. 作为前后端协作者，我希望两个应用通过同一个包名使用聊天消息、流式事件类型和运行时函数，以便共同维护聊天协议。
6. 作为维护者，我希望在 Nx 项目图中看到 Web 和 API 对共享包的依赖，以便判断共享代码变更的影响范围。
7. 作为全栈开发者，我希望在干净安装后用 `pnpm dev` 同时启动前后端，以便立即打开聊天页并通过开发代理访问 API。
8. 作为开发者，我希望能单独启动 API 或 Web，以便按需调试其中一个应用。
9. 作为修改共享聊天代码的开发者，我希望 Web 能刷新、API 能自动重启，以便快速验证同一处变更在两端的表现。
10. 作为本机开发者，我希望应用沿用仓库根目录的环境配置和相对数据库路径，以便继续使用已有配置和聊天历史。
11. 作为维护者，我希望用 `pnpm build` 先构建共享包，并在生成 Web 产物前检查类型，以便在产物交付前发现跨包类型错误。
12. 作为维护者，我希望 Nx 在输入相同时重用本地构建结果，并在共享源码或根 TypeScript 配置变化时重新构建受影响的项目，以便缩短反馈时间并避免使用过期产物。
13. 作为本机使用者，我希望在构建完成后运行 `pnpm start`，从一个地址打开聊天页并访问 API，以便按现有方式使用和恢复聊天会话。
14. 作为维护者，我希望生产启动直接执行编译后的 JavaScript，以便运行过程只依赖 Node.js 和应用运行时依赖。
15. 作为测试维护者，我希望 `pnpm test` 通过 Nx 执行一次 Vitest 测试并退出，以便得到明确的通过或失败结果。
16. 作为开发者，我希望 API 集成测试使用本地模型模拟接口和临时 SQLite，以便在没有百炼凭据时验证流式回复、工具调用和会话恢复。
17. 作为前期选址业务模型的维护者，我希望工程概算和财务原型继续使用各自的 Python 命令，以便独立运行和验证模型。

## 实施决策

- 保留 Node.js 24+，固定 pnpm `12.10.1`，Nx 及所用官方 Nx 插件统一固定为 `24.0.6`。将 Web、API 和共享聊天模块设为三个私有 pnpm 工作区包，Nx 项目名分别为 `web`、`api` 和 `chat`。Web 和 API 通过 `workspace:*` 声明对 `@rezoning-ai/chat` 的运行时依赖。
- 用 `pnpm import` 优先复用 npm 锁文件中满足现有依赖声明的版本，验证冻结安装后仅保留 pnpm 锁文件。沿用 pnpm 的依赖安装脚本审查，按实际依赖逐项决定是否允许执行。
- 保留 React、Nest 12、现有 Vite 和 `tsx` 开发入口。用 `@nx/js/typescript` 推断 API 和共享聊天包的构建及 Web 的类型检查。用 `@nx/vite/plugin` 推断 Web 构建和开发任务。Web 构建依赖 Web 类型检查，两个应用的生产构建依赖共享包的构建。构建使用 Nx 本地缓存，输入包含适用的共享源码和根 TypeScript 配置。
- 共享包用 `rezoning-source` 导出条件供开发和 Vitest 直接解析 TypeScript 源码。默认入口解析编译后的 JavaScript，生产类型解析使用生成的类型声明。Web 生产构建打包共享模块，API 编译产物位于 API 包内，由 Node.js 解析 API 的运行时依赖。
- 根命令 `pnpm dev` 通过 Nx 并行启动两个应用，并保留 `pnpm dev:api` 和 `pnpm dev:web`。API 开发入口从仓库根目录执行，沿用根环境配置、默认 SQLite 位置和端口。Vite 开发代理继续读取相同的 API 端口配置。移除 `concurrently`。
- `pnpm build` 调用 Nx 构建应用。构建成功后，`pnpm start` 直接运行编译后的 API，由 Nest 提供已构建的 Web 页面和现有 HTTP API。
- 使用 Vitest 5，并由 `@nx/vitest` 推断 API 的单次 `test` 目标。将现有四个 API 集成场景迁为顺序执行的 Vitest 测试，保留原有断言和用于验证重启恢复的会话历史。测试结束后关闭服务和数据库、清理临时数据并恢复测试修改的环境变量。
- 更新 README 的安装、运行和测试命令。新增 ADR 0007，记录三个包的边界及开发读源码、生产使用编译产物的取舍，承接 ADR 0006 的应用结构。

## 测试决策

- 以仓库根目录的公开命令、Nx 项目图、浏览器和 HTTP API 为验收入口。测试可观察的运行结果，例如退出状态、项目依赖边、缓存恢复、页面和 HTTP 响应。
- 在没有旧依赖目录和构建产物的临时副本中运行 `pnpm install --frozen-lockfile`、`pnpm build` 和 `pnpm test`。通过 Nx 项目图确认 `api → chat` 和 `web → chat`。重复构建并验证从本地缓存恢复产物，在临时副本中分别变更共享源码和根 TypeScript 配置，验证相关任务重新执行。
- 参考现有 API 集成测试，通过真正监听的本机 API、模拟 Chat Completions 接口和临时 SQLite 验证四个场景：流式片段与多轮上下文、时间工具调用、中断和同一消息重试、重启后的聊天会话与未完成回复恢复。保留已有的重复提交和会话隔离断言。
- 在首次构建前运行 `pnpm dev`，确认聊天页能打开并经 Vite 代理访问 API，修改共享源码后 Web 更新且 API 重启。用不同的 API 端口再检查配置和代理是否一致。
- 构建后运行 `pnpm start`，确认 Nest 在同一端口提供聊天页和 `/api/config`。启动验收使用临时数据库，以免写入现有聊天记录。
