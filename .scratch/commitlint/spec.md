# 基于 Commitlint 规范 Git 提交记录

Status: accepted

Labels: ready-for-agent

## 问题陈述

REZoningAI 的开发者已经在手写提交中使用 `docs:`、`build:` 和 `fix:` 等类型，但仓库尚无自动检查。提交消息漏写类型或标题时，Git 仍会创建提交，维护者只能在浏览历史或审查变更时发现。仓库当前只有本地分支，维护者也需要一条可以立即检查提交区间、将来可供 CI 复用的命令。

## 解决方案

开发者正常安装根工作区依赖后，Git 在创建提交时通过 Husky 调用 Commitlint。手写消息采用 Conventional Commits。格式错误会阻止提交并给出诊断，只有警告时仍可提交。维护者可用同一套规则检查指定提交区间。README 提供消息示例、钩子恢复方法和区间检查用法。

## 用户故事

1. 作为首次克隆仓库的开发者，我希望冻结安装依赖时自动启用提交校验，以便按原有安装流程开始工作。
2. 作为已有本地工作区的开发者，我希望能手动重新启用钩子，以便恢复提交时的校验。
3. 作为提交者，我希望格式错误在执行 Git 提交时立即显示，以便在创建提交前修正消息。
4. 作为提交者，我希望诊断能指出违反的规则，以便区分类型、标题等字段的问题。
5. 作为提交者，我希望遇到未支持的类型或缺失的标题时 Git 拒绝提交，以便保持历史格式一致。
6. 作为提交者，我希望只有警告时仍能完成提交，以便保留官方预设区分错误与警告的行为。
7. 作为主要用中文协作的开发者，我希望可以写中文标题，以便直接用团队日常使用的语言描述改动。
8. 作为习惯用英语写提交的开发者，我希望可以继续写英文标题，以便沿用现有历史的写法。
9. 作为修改单个模块的开发者，我希望能用 scope 标明 `api`、`web` 或 `chat`，以便从历史中快速识别影响范围。
10. 作为调整整个工作区的开发者，我希望可以省略 scope，以便描述跨模块的改动。
11. 作为维护工作区结构的开发者，我希望符合预设格式的新 scope 可以直接使用，以便增加模块时无需同步维护白名单。
12. 作为合并或回退分支的开发者，我希望 Git 生成的标准合并和回退消息按默认规则通过，以便继续使用 Git 自带操作。
13. 作为整理提交历史的开发者，我希望可以使用 `fixup!` 和 `squash!` 消息，以便继续用 Git 的自动压缩流程整理提交。
14. 作为维护者，我希望纯版本号消息保留预设的豁免，以便检查区间时能处理这类消息。
15. 作为审查一组提交的维护者，我希望指定基准和终点来校验提交区间，以便检查本轮变更引入的消息。
16. 作为维护者，我希望区间检查能通过退出状态区分合规区间与包含错误的区间，以便将它接入自动化。
17. 作为将来接入 CI 的维护者，我希望 Git 钩子和区间命令共用规则，以便本地反馈和自动检查一致。
18. 作为新贡献者，我希望在 README 中找到可用的中英文消息示例和校验命令，以便独立完成首次提交和排查。
19. 作为仓库维护者，我希望在独立 worktree 中审查实现，以便将提交规范的改动与 Nx、pnpm 迁移工作区隔离。

## 实施决策

- 以当前提交 `e62bdee` 为基线创建 `codex/commitlint` 分支和独立 worktree，功能改动在该 worktree 交付。
- 延续 ADR 0007 的 Nx 与 pnpm 工作区。将 Commitlint CLI 和 Conventional Commits 配置预设作为 21.x 根开发依赖，将 Husky 作为 9.x 根开发依赖，并更新 pnpm 锁文件。沿用 Node.js 24+ 和 pnpm 12.10.1。
- 根配置使用 ESM，直接继承官方预设。提交标题由类型、可选 scope 和主题组成。scope 推荐使用现有模块名且无白名单，主题可使用中文或英文。类型、长度、大小写、默认豁免和错误级别均由预设决定。
- 根工作区通过 `prepare` 安装 Husky。Git 的 `commit-msg` 钩子把实际提交消息文件交给根脚本 `lint:commits`。根脚本直接运行 Commitlint，使钩子、手动检查和未来的 CI 都读取同一份配置。
- 开发者在仓库根目录用 `pnpm run lint:commits --from BASE --to HEAD` 检查 Git 的 `BASE..HEAD` 区间。两种校验入口都沿用默认退出行为，只有报告错误时才会因消息违规而失败。
- 在 README 记录中英文格式示例、区间命令，以及用 `pnpm run prepare` 恢复钩子的方法。

## 测试决策

- 以根目录冻结安装后的真实 Git 提交和根区间命令为验收入口。断言 Git 是否创建提交、用户是否看到诊断，以及区间命令的退出状态。参考 Nx 与 pnpm 迁移验收，使用干净的临时副本和仓库公开命令。
- 在临时独立克隆执行 `pnpm install --frozen-lockfile`。用真实提交验证中英文标题、有无 scope 及预设允许的自定义 scope 均能通过，`fixup!` 消息被豁免，仅触发警告的消息提示后仍能提交。无效类型和缺少标题的消息应产生错误并阻止提交。
- 在同一临时克隆运行区间命令。合规区间和只有警告的区间均返回成功，包含错误的区间返回非零。验收用的提交留在临时克隆。
- 运行 `pnpm test`，确认现有 Nx 与 Vitest 测试入口通过。检查功能改动位于独立 worktree。

## 范围之外

- 配置 Git remote、CI 工作流或托管平台的合并规则。
- 改写现有提交历史，或给历史消息补充 scope。
- 接入版本发布或自动生成变更日志。
- 修改选址业务、应用代码、聊天协议或数据库结构。
