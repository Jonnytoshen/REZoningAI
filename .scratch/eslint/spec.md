# 为 REZoningAI 接入 Nx ESLint

Status: resolved

## 问题陈述

Agent 工作区已用 Nx 管理 Web、API 和共享聊天包，但开发者没有统一的代码静态检查入口。现有 Git 钩子只校验提交消息，不能在提交前发现代码违规。三个项目共用 TypeScript，但 Web 使用 React，API 使用 NestJS，规则需要匹配各自的语言和框架，不能把 Web 的规则套用到其他项目。

## 解决方案

给现有的 `web`、`api` 和 `chat` 增加由 Nx 推断的可缓存 `lint` 任务，并按项目采用 Nx 官方默认规则。开发者可以单独检查一个项目，也可以用 `pnpm lint` 检查三个项目。提交前复用同一个全量入口，代码检查通过后仍由 Commitlint 校验提交消息。接入时最小化修复已有错误，使首次全量检查即可通过。

## 用户故事

1. 作为贡献者，我希望用一条命令检查三个项目，以便在提交前一次看完所有诊断。
2. 作为 Web 开发者，我希望能单独检查 Web，以便只改前端时快速获得反馈。
3. 作为 API 开发者，我希望能单独检查 API，以便独立处理服务端问题。
4. 作为共享聊天包维护者，我希望共享包有自己的检查任务，以便无需运行两个应用也能检查共享代码。
5. 作为 Web 开发者，我希望 React 代码采用 Nx 官方的 React 默认规则，以便发现框架特有的问题。
6. 作为 API 开发者，我希望 NestJS 代码沿用 Nx 对 Nest/Node 项目的默认规则，以便不受仅适用于 React 的规则干扰。
7. 作为共享聊天包维护者，我希望沿用 Nx 可构建 TypeScript 库的默认规则，以便共享层不引入应用框架规则。
8. 作为贡献者，我希望项目内的测试和 JS/TS 配置也接受检查，以便源码之外的代码问题不会被遗漏。
9. 作为维护者，我希望保留 Nx 默认的模块边界规则，以便检查项目间的不当依赖。
10. 作为贡献者，我希望构建产物和独立 Python 原型不参与本次检查，以便生成文件和其他工具链不干扰提交。
11. 作为首次使用该功能的开发者，我希望冻结安装后全量检查就能通过，以便诊断能反映当前修改而非已知存量错误。
12. 作为经常运行检查的开发者，我希望未变化的项目可命中 Nx 缓存，以便重复检查和提交更快。
13. 作为维护者，我希望共享规则改动后旧缓存失效，以便每个项目按新规则重新检查。
14. 作为提交者，我希望检查失败时 Git 不创建提交，并输出规则诊断，以便先修正问题再提交。
15. 作为提交者，我希望提交钩子和手动命令检查相同的工作区内容，以便在终端复现失败，即使错误出现在未暂存的编辑里。
16. 作为提交者，我希望只有规则警告时仍可提交，以便保持官方预设对警告和错误的区分。
17. 作为提交者，我希望钩子不改写文件或改变暂存内容，以便由我决定实际提交哪些修改。
18. 作为维护者，我希望代码合规时提交消息仍按原有规则检查，以便现有历史约定不受影响。
19. 作为新贡献者，我希望 README 说明检查命令、触发范围和钩子恢复方式，以便自行运行和排查。
20. 作为仓库维护者，我希望实现放在独立 worktree 且不自动提交或推送，以便先审查改动，再决定是否集成。

## 实施决策

- 以当前 `main` 为基线，在独立 worktree 的 `codex/eslint` 分支实施；不改主工作区的实现，不自动提交或推送。
- 沿用 ADR 0007 的 Nx 与 pnpm 工作区。在根工作区引入与现有 Nx 一致的 `@nx/eslint` 和 `@nx/eslint-plugin`（均为 `24.0.6`），按该版本生成器的默认版本范围安装 ESLint 和相关开发依赖，更新 pnpm 锁文件，不升级现有 Nx。
- 使用 ESLint Flat Config。根配置共享 Nx 默认的 JS/TS 预设和模块边界规则；Web 叠加 Nx 的 `flat/react`，API 对齐 Nx Nest/Node 生成器默认配置，共享聊天包对齐 Nx 可构建 TypeScript 库生成器默认配置。框架规则只作用于适用项目；只排除生成物，不添加自定义规则、不降低规则级别、不额外启用类型感知检查。
- 注册 `@nx/eslint/plugin`，由各项目配置推断可缓存的 `lint`，不新增独立 Nx 项目。根命令 `pnpm lint` 运行 `nx run-many -t lint -p web api chat`；单项目入口为 `pnpm exec nx lint <project>`。
- 按官方默认规则最小化修复存量错误，不以规则豁免或忽略源码代替修复；保留默认警告行为。若修复会改变业务行为，先确认再改。
- 在现有 Husky 设置中增加 `pre-commit`，直接执行 `pnpm lint`。任何提交都检查三个项目的完整工作区，包括文档提交和未暂存的代码；不使用自动修复，不修改暂存区。保留现有 `commit-msg` 钩子。
- README 记录全量与单项目命令、提交钩子的工作区检查范围，以及用 `pnpm run prepare` 恢复钩子的方法。验收结果记入实施工单。

## 测试决策

- 从开发者实际使用的入口验收：以 Nx 命令和真实 Git 提交的诊断、退出状态及是否创建提交为准，不针对 ESLint 配置的内部结构编写测试。参考 Nx 与 pnpm 迁移、Commitlint 接入的验收方式，使用干净的临时克隆验证安装与钩子。
- 执行 `pnpm install --frozen-lockfile` 后，确认三个项目都能单独执行推断出的 `lint`，全量检查在跳过 Nx 缓存时通过。用临时违规分别验证 Web 的 React 规则和 API、共享包的 TypeScript 规则能报告错误；也确认项目内测试和配置会被检查。
- 用相同输入连续运行全量命令，确认 Nx 缓存命中；在临时副本更改共享 ESLint 配置，确认相关 lint 任务重新执行，不复用旧结果。
- 在临时克隆留下一处未暂存的代码错误，尝试提交一项无关的已暂存改动，确认 lint 输出诊断且未创建提交。修复后用非法提交消息重试，确认 Commitlint 单独阻止提交；用合规代码与消息重试，确认提交成功。验证仅有规则警告时不阻止提交，钩子不改写文件或暂存内容。
- 运行现有 `pnpm test` 和 `pnpm build`，确认 Agent 的测试与构建入口不受影响。

## 范围之外

- 检查根目录工具脚本或独立 Python 原型；新增格式化工具、格式规则或自定义 lint 规则。
- 配置 CI、远程仓库或合并门禁；修改 Commitlint 的规则与豁免。
- 修改选址业务、聊天协议、API 或数据库结构。
